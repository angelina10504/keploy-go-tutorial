## Keploy in 60 seconds

Three words you'll see everywhere in this tutorial:

<ConceptGrid>
  <Concept icon="file-text" title="Test case">
    One request you sent, plus the response your app gave back. Saved as a readable YAML file.
  </Concept>
  <Concept icon="database" title="Mock">
    A saved conversation between your app and the database: "the app asked this, MongoDB answered that."
  </Concept>
  <Concept icon="shuffle" title="Noise">
    Fields that change every run, like timestamps. Keploy skips comparing them so tests don't fail for no reason.
  </Concept>
</ConceptGrid>

And the whole idea in one picture. Switch between the two modes:

## Why this is useful for Go developers

API tests usually cost you two things: writing the test code, and running a database (or hand-written fakes) every time the tests run.

Keploy removes both. You use your app once while Keploy records, and you get tests *and* database mocks for free. Replaying them needs no database at all, which makes them fast and easy to run anywhere, including CI.

## Before you start

You need:

- A Mac with Apple Silicon (Keploy runs natively on it)
- [Homebrew](https://brew.sh)
- Go: `brew install go`
- MongoDB: `mongod` available in your terminal
- A free Keploy account (your first `keploy record` asks you to sign in)

<Callout type="warning" title="Keep the project out of iCloud">
If your Mac syncs **Desktop** and **Documents** to iCloud, don't clone there. iCloud can move files to the cloud to save space, and your app will hang while macOS downloads them one by one. That cost me a confusing five-minute hang on another project. Use a folder like `~/dev` instead.
</Callout>

## Not on a Mac?

- **Windows (x86-64):** Keploy also runs natively on Windows. Follow the [official Windows install guide](https://keploy.io/docs/installation/windows-installation/), then continue from "Clone the sample app". I haven't tested the Windows path myself, so some commands (like `sed -i ''` and `mongod --fork`) will differ.
- **Linux / WSL:** the [official Gin + MongoDB quickstart](https://keploy.io/docs/quickstart/samples-gin/) covers this directly.
- **Intel Mac:** there's no native build. Keploy's docs recommend [running it inside Lima](https://keploy.io/docs/installation/macos-installation/).

## Run the quickstart

<Steps>

### Install Keploy

```bash
curl --silent -O -L https://keploy.io/install.sh && source install.sh
keploy -v
```

You should see a version number.

<Explain>
On macOS, Keploy intercepts traffic by loading a small library into your app when it starts. That's why there's no `sudo`, no VM and no Docker. (On Linux it uses a kernel feature called eBPF instead.)
</Explain>

### Clone the sample app

```bash
mkdir -p ~/dev && cd ~/dev
git clone https://github.com/keploy/samples-go.git
cd samples-go/gin-mongo
go mod download
```

<Explain>
This is a tiny URL shortener built with **Gin** (Go's equivalent of Express). You send it a long URL, and it saves it in MongoDB and gives you a short link. `go mod download` fetches its dependencies, like `npm install`.
</Explain>

### Point the app at your local MongoDB

```bash
sed -i '' 's/mongoDb:27017/127.0.0.1:27017/' main.go
grep -n "27017" main.go
```

The `grep` should now show `127.0.0.1:27017`.

<Explain>
The sample is written for Docker, where the database lives at `mongoDb:27017` (a Docker container name). On your Mac, the database is on your own machine, at `127.0.0.1:27017`.
</Explain>

<Callout type="tip" title="Use 127.0.0.1, not localhost">
The docs point to a line number for this change, but the code has moved since, so search for the string instead. And prefer `127.0.0.1`: on macOS, `localhost` tries IPv6 (`::1`) first, while the MongoDB below only listens on IPv4. With `localhost`, Keploy quietly reroutes the connection and prints a warning.
</Callout>

### Start a throwaway MongoDB

```bash
mkdir -p ~/mongo-keploy-go
mongod --dbpath ~/mongo-keploy-go --bind_ip 127.0.0.1 --port 27017 \
  --fork --logpath ~/mongo-keploy-go/mongod.log
```

Look for `child process started successfully`.

<Explain>
This starts a fresh, empty database just for this tutorial, so nothing real gets touched. `--fork` runs it in the background so you get your terminal back.
</Explain>

### Record some traffic

In your first terminal tab:

```bash
keploy record -c "go run main.go handler.go"
```

Wait until you see:

```text
INFO  Started ingress forwarding  {"orig_port": 8080, ...}
```

Now open a **second tab** and use the API:

```bash
curl -X POST http://localhost:8080/url \
  -H 'content-type: application/json' \
  -d '{"url":"https://google.com"}'
```

You'll get back a short link. Mine was `http://localhost:8080/Lhr4BWAi`, the exact same code as in the official docs. Open it:

```bash
curl -i http://localhost:8080/Lhr4BWAi
```

You should get a `303` redirect to Google. Back in the first tab, Keploy confirms each capture:

```text
INFO Keploy has captured test cases … {"testcase name": "post-url-1"}
INFO Keploy has captured test cases … {"testcase name": "get-lhr4bwai-1"}
```

<Explain>
`-c` is the command Keploy uses to start your app, so Keploy can sit in the middle from the first second. Each curl became one **test case**. Behind the scenes, the app also talked to MongoDB (to save and look up the link), and Keploy saved those conversations as **mocks**.
</Explain>

<Callout type="warning" title="Wait for the capture lines before stopping">
If you press Ctrl+C before sending any requests, nothing gets recorded, and the auto-replay afterwards prints a scary *"Keploy was never loaded into your application"* warning that blames macOS. The real cause is simply an empty recording.
</Callout>

### Stop recording and watch the auto-replay

Press **Ctrl+C once** in the first tab. Keploy immediately replays what it just recorded:

```text
TESTRUN SUMMARY. For test-set: "test-set-1"
  Total tests:        2
  Total test passed:  2
  Total test failed:  0
```

<Explain title="What just happened? (my a-ha moment)">
The response to `POST /url` includes a timestamp (`ts`) that's different every time. The official quickstart says this will fail and you need to add `body.ts` to the noise list by hand. On Keploy 3.8.47, the automatic replay spotted the changing field and added it to the noise list for me. No manual step.
</Explain>

### Look inside a test

```text
keploy/
├── test-set-0/          ← ships with the sample repo
└── test-set-1/          ← yours
    ├── tests/
    │   ├── post-url-1.yaml
    │   └── get-lhr4bwai-1.yaml
    ├── mocks.yaml       ← the recorded MongoDB conversations
    └── mappings.yaml    ← which mocks belong to which test
```

Open `tests/post-url-1.yaml`. Trimmed down, it looks like this:

```yaml title="keploy/test-set-1/tests/post-url-1.yaml (trimmed)"
kind: Http
name: post-url-1
spec:
  req:                    # ← the request you sent with curl
    method: POST
    url: http://localhost:8080/url
    body: '{"url":"https://google.com"}'
  resp:                   # ← what the app answered: the expected result
    status_code: 200
    body: '{"ts":…,"url":"http://localhost:8080/Lhr4BWAi"}'
  assertions:
    noise:                # ← fields Keploy won't compare
      body.ts: []
      header.Date: []
```

That's all a Keploy test is: a request, the expected response, and a list of fields to ignore.

`test-set-0` isn't something you created. It comes with the `samples-go` repo, so `keploy test` will run it too.

### Run the tests yourself

```bash
keploy test -c "go run main.go handler.go" --delay 10 \
  --disableMockUpload --disableReportUpload
```

```text
COMPLETE TESTRUN SUMMARY.
  Total tests: 4
  Total test passed: 4
  Total test failed: 0

  "test-set-0"    2    2    0
  "test-set-1"    2    2    0
```

<Explain>
Keploy started your app, re-sent every saved request, answered the app's database calls from `mocks.yaml`, and compared each response with the saved one. `--delay 10` gives the app 10 seconds to start before the first request arrives.
</Explain>

<Callout type="tip" title="Keep your mocks on your machine">
By default, Keploy uploads your mocks and test report to your Keploy account (you'll see `Mock uploaded successfully` in the logs). The two `--disable…Upload` flags keep everything local. There's nothing secret in this sample, but in a real app your mocks can contain API keys and user data.
</Callout>

### The proof: switch the database off

```bash
mongosh --quiet admin --eval 'db.shutdownServer()'
pgrep -l mongod   # prints nothing = MongoDB is off

keploy test -c "go run main.go handler.go" --delay 10 \
  --disableMockUpload --disableReportUpload
```

```text
COMPLETE TESTRUN SUMMARY.
  Total tests: 4
  Total test passed: 4
  Total test failed: 0
```

Still 4 out of 4.

<Explain title="Why this matters">
Your app still thinks it's talking to MongoDB, but every reply now comes from `mocks.yaml`. That's the whole point: **your API tests no longer need a database to run.** They work on any laptop or CI runner, with no setup.
</Explain>

</Steps>

## Messages that look scary but aren't

<Messages>
  <Message text="GET /keploy/__readiness_probe__ → 404">
    Before replaying, Keploy pings your app to check it's up. The sample's `GET /:param` route catches the ping and returns 404. That just means the app answered.
  </Message>
  <Message text="sync /dev/stderr: inappropriate ioctl for device">
    Printed when the app shuts down between test sets. Harmless.
  </Message>
  <Message text="You are already on the latest version of Keploy">
    Keploy checks for updates on every run. Mine updated itself from 3.8.44 to 3.8.47 between two days of testing, so check `keploy -v` if your logs look different from someone else's.
  </Message>
</Messages>

## Where to go next

- **Record more endpoints.** Every request you make while recording becomes another test.
- **Run it in CI.** By default, Keploy reports some broken tests as "obsolete" rather than "failed", and the run still exits 0. Add `--strict-failure` so a broken replay actually fails your pipeline. I wrote about [how I found that out on my MERN app](https://dev.to/angelina_gupta/i-ran-keploy-on-my-mern-app-the-scariest-result-was-a-green-one-331e).
- **Read the docs.** The [Keploy documentation](https://keploy.io/docs/) covers noise configuration, CI integration, and more quickstarts.
